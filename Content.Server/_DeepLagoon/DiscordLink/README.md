# Обязательный допуск Discord → whitelist

В рабочем пакете (`FullRelease=true`) при `discord_link.enabled=true` игрок до допуска видит отдельный экран проверки вместо лобби. Окно выдаёт одноразовый код с кнопкой копирования в буфер обмена. Закрыть его без допуска нельзя; можно отключиться от сервера. После привязки требуется допуск whitelist. Проверка открытых окон повторяется каждые три секунды; бот также обновляет допуск после привязки и выдачи whitelist. После одобрения окно закрывается и открывается лобби.

Запрет реализован и на сервере: клиент не может закрытием окна получить допуск к лобби, раунду или наблюдению. Авторизованный аккаунт SS14 обязателен.

Отзыв whitelist через менеджер или API немедленно удаляет допуск и отключает действующую сессию, включая уже вошедшего в раунд игрока. Отвязка Discord также отключает ранее допущенную сессию. Асинхронный результат старой проверки не может вернуть отозванный допуск. Прямые ручные изменения SQL в обход менеджера не создают это событие; для штатного отзыва используйте административный API/команду.

Объединение аккаунтов выполняется отдельным заданием и не удерживает общий семафор API во время внешнего процесса. HTTP ожидает не более 20 секунд; `409 merge_pending` означает, что нужно повторить **тот же** код, а не начинать другое объединение. Не более четырёх заданий находятся в памяти одновременно. Префлайт ограничен 10 секундами, ожидание сохранений — 30 секундами. Реальный worker после HTTP timeout не уничтожается: результат транзакции проверяется по журналу при повторе. Завершившееся или аварийно прерванное задание можно безопасно возобновить тем же кодом после рестарта; durable pending и journal удалять вручную нельзя.

Пока durable plan не завершён, изменения привязки, whitelist, LC и модерации затронутых аккаунтов отвечают `merge_pending`; остальные аккаунты и продление донатерских статусов обслуживаются. Worker должен сохранять существующий идемпотентный PostgreSQL journal и общий advisory lock. Перед обновлением worker и Station нужен согласованный контракт: stdin `source_uid/target_uid`, stdout `ok/source_uid/target_uid`, exit 0 только при подтверждённом результате.

Статус Boost/Boosty кешируется как абсолютное время окончания lease. Горячий путь начисления LC не обращается к SQLite каждый тик; истечение lease проверяется по времени даже без очередного запроса бота. Изменения статуса и привязки инвалидируют кеш.

В Dev-сборках (символ `DEVELOPMENT`, то есть сборка без `FullRelease=true`, включая локальный Release) привязка и whitelist при подключении полностью пропускаются независимо от конфига. Этот режим не меняет записи привязок и whitelist в базе. Серверный установщик GUI использует полноценный пакет FullRelease.

Проверки:

```powershell
dotnet test Content.IntegrationTests/Content.IntegrationTests.csproj -c Release --filter "FullyQualifiedName~DiscordLobbyAdmissionTests|FullyQualifiedName~DiscordLinkStoreTests"
```

Тест production-допуска использует тестовую конфигурацию системы с выключенным Dev-обходом: движок FullRelease не поддерживает dummy-сессии. Отдельный тест проверяет реальный обход в Dev.

## Webhook всех операций Lagoon Coin

В серверном `server_config.toml` задайте:

```toml
[discord]
lagoon_coin_webhook = "https://discord.com/api/webhooks/WEBHOOK_ID/WEBHOOK_TOKEN"
```

Используйте приватный канал финансового журнала. Пустое значение отключает отправку. Адрес конфиденциальный серверный CVar, клиентам не передаётся и в сообщения об ошибках не выводится. У слотов с общей игровой БД должен быть одинаковый webhook.

Логируются все подтверждённые изменения LC: начисление через Ready, игровое время и цели; выдача через консоль или бот; снятие; будущая покупка LC и траты за LC. Сообщение содержит ник игрока, сумму со знаком, точный баланс после операции, источник, автора, причину, время UTC и ключ операции. UID игроков и служебный Discord ID автора в webhook не выводятся; в базе остаются для аудита. Упоминания отключены. Нулевые служебные записи времени и отклонённые изменения баланс не меняют и не отправляются.

Запись для отправки создаётся в той же транзакции, что баланс LC. Discord недоступен — финансовая операция остаётся подтверждённой, а уведомление ждёт повторной отправки в БД. Очередь сохраняется после перезапуска; временная блокировка записи предотвращает одновременную отправку несколькими слотами. После обработанного сетевого сбоя повтор планируется через 30 секунд, при ограничении Discord учитывается Retry-After; двухминутная блокировка нужна только для восстановления после аварийного завершения процесса. Повтор финансового запроса с тем же ключом не добавляет второе уведомление. При потере HTTP-ответа после принятия Discord возможен повтор доставки: сверяйте одинаковые ключи операций.

Миграция `LagoonCoinWebhookDelivery` добавляет баланс после операции и состояние доставки. Старый журнал до миграции не рассылается. Новые операции сохраняются для отправки даже при пустом webhook и будут доставлены после его настройки.

Задел для будущего магазина: `LagoonCoinSystem.RecordPurchase` вызывается только после проверки внешнего платежа со стабильным ID заказа (`purchase:<id>`); `Spend` подтверждает списание перед выдачей товара (`spend:<id>`). Оба пути используют тот же атомарный журнал и webhook. Внешний платёжный сервис и магазин пока не реализованы.
